## 2. Embedding更新范围

现有向量由资产多视图与检索文本联合计算。风格体系及其文本发生变化时，应重新计算相关联合向量，仅修改数据库metadata不能替代这一步。

下一轮更新先冻结全库38,497件的正式字段，并按以下规则处理：

1. 以asset_uid对齐现有索引和最新正式库，检查图片内容SHA、检索文本、模型和后端契约。
2. 完全相同的输入复用旧向量；新增资产或检索文本/图片变化的资产重新计算。
3. 将最新一级、二级多标签风格以及主题色、材质观察整理进检索描述；区分来源参考、视觉观察和unknown原因。
4. 不只针对最近新增明确风格的7,019件：旧索引仍基于更早风格体系，其他资产也可能需要更新文本。
5. unknown_style继续保留明确状态与较低风格匹配优先级；不把fallback解释成一种真实设计风格。

正式标注的修正与Embedding更新分别验收。后续Sol候选未正式合并前，不混入冻结输入。

## 3. 资源预算

| 资源 | 建议配置与用途 |
|---|---|
| GPU | 一张可执行，两张可启动两个同模型副本并行处理；优先复用已有验证后端的H100窗口 |
| GPU显存 | 每副本建议先预留16GiB作为调度预算，再以100–200件真实输入测峰值；历史同后端启动占用为5,825MiB/副本，这不是运行峰值 |
| CPU | 建议8–16线程，用于解码、校验、文本准备、索引写入和验收 |
| 主机内存 | 建议32GiB；准备全量标注、校验新旧记录和运行服务需分别考虑内存峰值 |
| 磁盘 | 建议预留20–40GiB，用于输入冻结、服务依赖、新索引、校验产物和少量补渲染；保留旧索引，不复制全量mesh |
| 模型 | 沿用Qwen3-VL-Embedding-2B Q8_0、2048维及既有mmproj，核对模型和二进制SHA |
| 外部标注API | 向量计算本身不需要Luna/Sol API；未知风格再校准是独立的已授权Sol API任务 |

上述为实施预算，不是已分配的GPU资源或经过本轮实测的最低配置。现有模型与渲染输入先检查再复用，缺失项单列。

历史双卡首批64件的吞吐约2.73件/秒，只代表该首批。当作全量速度会忽略读盘、图像数量差异、补渲染、服务恢复和验收耗时。正式运行前使用100–200件跨来源真实输入测量吞吐、峰值显存和失败率，再估算完整时长。

若改用RTX5090或新的llama.cpp构建，先检查设备实际身份及CUDA/内核支持，并做与旧后端的同模型向量兼容性检验。已验证的旧H100证据不能代替新后端的现场检验。

## 4. e区与g区的数据与续跑

e区、g区的`/data`各自独立，同名路径不代表文件共享。g区执行时只传输所需模型依赖、冻结文本和渲染图，结果回传e区校验后再构建正式索引。

2026-11-16检查时，CPU本机`/mnt/aoss2`返回ENOTCONN（errno 107）；跨区方案须先恢复中转，或使用经过身份核验的SSH传输，不能把中转目录当成当前可用渠道。

队列以冻结输入指纹、已flush向量和checkpoint续跑。容器重建后重新核对设备、模型、输入与后端契约，再接续未完成项，不重复计算已校验结果。
